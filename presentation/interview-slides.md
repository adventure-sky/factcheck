## Slide 2 — 問題定義（0:10–0:35）

**標題**
現有工具只告訴你答案，不教你思考

**左欄 — 現有痛點**
- 台灣每天有大量假訊息透過 LINE 群組傳播
- 現有平台（Cofacts、MyGoPen）只給「真／假」結論
- 使用者不知道「為什麼是假的」，下次還是會被騙

**右欄 — 市場空缺**
> 缺少一個「教你怎麼判斷」而不只是給答案的工具

> **講稿**
> 台灣的假訊息問題很嚴重，但現有工具有一個共同缺點：它們只給答案，不培養判斷力。我想填補這個空缺。

## Slide 3 — 解決方案（0:35–1:05）

**標題**
三大核心功能

| 功能 | 說明 |
|------|------|
| 🔍 逐步引導查核 | AI 拆解每個判斷步驟，教使用者識讀邏輯，而非只給結論 |

> **講稿**

## Slide 4 — 技術架構（1:05–1:20）

**標題**
全端獨立開發

| 層級    | 技術                                    |
| ----- | ------------------------------------- |
| 前端    | HTML / CSS / JS — Intelligence HUD 設計 |
| 後端    | Python FastAPI — 5 個 Agent 類別，asyncio.gather 並行 |
| AI 模型 | Groq — gpt-oss-120b（文字）+ qwen3.8-27b（圖片）|
| RAG   | ChromaDB × 265,952 筆 Cofacts 查核資料     |
| 圖片 AI | AI or Not API（98.9% 準確率）              |
| 部署    | Railway — Docker 容器化                  |

**重點**
從 0 到 1 獨立完成前後端開發、AI 整合與雲端部署

**Agent 架構說明（可延伸說明）**

後端共 5 個 Agent 類別，各自負責單一職責：

| Agent | 職責 |
|-------|------|
| RAGAgent | 查 ChromaDB 向量資料庫 |
| FactCheckAgent | 呼叫 Google Fact Check API |
| WebSearchAgent | 呼叫 Google Custom Search |
| SynthesisAgent | 匯整三方結果，呼叫 Groq 生成報告 |
| VisionAgent | 圖片 AI 辨識（AI or Not + Groq Vision）|

前三個用 `asyncio.gather` 同時執行，不串行等待，再由 SynthesisAgent 統一匯整。

> **講稿**
> 後端我把每個資料來源拆成獨立的 Agent 類別，用 Python 的 asyncio.gather 讓三個查詢同時執行，避免串行等待。最後由 SynthesisAgent 統一匯整，送給 Groq 生成報告。

## Slide 5 — 上線取捨與維運（1:20–1:42）

**標題**
從本地到上線：取捨與故障處理

| 功能 | 本地端 | 生產環境 | 取捨原因 |
|------|--------|----------|----------|
| RAG 語義檢索 ＋ 儀表板 | ✅ 265,952 筆 | ⚠️ 優雅降級 | 向量庫 2.1GB 加上模型依賴，超出免費方案 0.5GB RAM 上限 |
| Web 搜尋佐證 | ✅ 即時搜尋 | ⚠️ 優雅降級 | Google Cloud 即使用免費額度也須綁定付款方式 |
| AI 查核分析 | ✅ 正常 | ✅ 正常 | 雲端 API，無本地資源限制 |
| AI 圖片辨識 | ✅ 正常 | ✅ 正常 | 同上 |

**上線後的真實故障**
上游 AI 供應商停止提供原本使用的模型 → 查核功能全數失效，
但健康檢查與首頁一切正常（錯誤被包在 HTTP 200 的回應內）

**兩個原則**
1. 資料密集型功能「優雅降級」而非讓系統崩潰
2. 部署驗證要跑核心業務流程 — 健康檢查通過不等於功能正常

> **講稿**
> 上線時我遇到兩類問題。第一類是資源取捨：RAG 需要的向量庫和模型超出免費方案的記憶體上限，所以我讓它優雅降級，回傳空結果而不是讓系統崩潰。
> 第二類更有意思——上線後供應商把我用的模型下架了，查核功能全壞，但健康檢查和首頁都正常，因為錯誤被包在 HTTP 200 裡面。這件事讓我建立一個習慣：驗證部署一定要實際跑一次核心流程。

**可延伸說明（被追問時使用）**

故障的診斷與修復過程：

| 步驟 | 內容 |
|------|------|
| 發現 | 健康檢查、首頁、儀表板三項全綠，但實際送一筆查核才看到供應商回傳「模型不存在」 |
| 選替代 | 用真實的 prompt 實測候選模型，比較判定準確度、中文品質與回應時間 |
| 踩到限制一 | 候選 A 有「每分鐘輸出 token」上限，而完整查核報告的長度剛好超過，必然被拒 |
| 踩到限制二 | 候選 B 是推理模型，思考過程與答案共用輸出額度且浮動達 5 倍，導致 JSON 間歇被截斷、約 50% 失敗 |
| 修復 | 降低推理強度使其穩定，並為每個呼叫點設定明確的輸出上限 |
| 驗證 | 連續跑完整流程 3 輪、6 條路徑全通，再實測生產環境 5 個案例 |

延伸心得：間歇性失敗比完全失敗更難處理——隔離測試會通過，必須用連續呼叫的真實情境才重現得出來。
